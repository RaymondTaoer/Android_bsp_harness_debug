# 设计说明：这个 harness 想解决什么

## 1. 问题不是"模型不会写代码"

在一棵几百 GB 的 Android / BSP 树上，模型翻车的方式高度集中在四类，且都不是语法错误：

| 失败模式 | 真实表现 | 后果 |
|---|---|---|
| **过期索引当事实** | 用三天前的索引回答"这个函数谁调用" | 改错位置，理由还很充分 |
| **未执行的构建当证据** | 贴一段编译日志，但那是上一次的 | 交付了根本没编译过的代码 |
| **"无法判定"讲成"没问题"** | 设备不在线，就说"应该没问题" | 问题留到客户现场 |
| **范围越界** | 顺手改了 feature 之外的文件 | 别人一同步就冲突，还找不到是谁改的 |

所以这套框架的核心不是"让 AI 更强"，而是**让 AI 的结论可以被验证、可以被反驳**。

## 2. 四段证据（STATIC → BUILD → DEVICE → FEATURE）

每个 feature 的验收脚本 `verify-<feature>.sh` 固定按四段输出，缺一段就是 `INCOMPLETE`：

| 段 | 回答的问题 | 谁提供 | 判定依据 |
|---|---|---|---|
| **STATIC** | 代码里的符号/引用是否如声称的那样 | `cg-assert` | 索引可查询 + 符号存在 + 影响面不越界 |
| **BUILD** | 构建是否真的成功、产物是否真的更新 | `verify-build` | 成功标记 + 产物 mtime 晚于标记 + 无 `error:` |
| **DEVICE** | 设备上实际是什么状态 | `adb` 只读查询 | `getprop` / `dumpsys` 实际输出 |
| **FEATURE** | 功能指标是否达标 | `assertions.tsv` | **人写的阈值**，脚本只做比较 |

关键点：**每段只有三种结论 `PASS` / `FAIL` / `SKIP`**，任何一段 `SKIP` 都会把整体压成 `INCOMPLETE`。
`INCOMPLETE` 不是"通过"的近义词，它就是"没有结论"。

### 为什么阈值必须由人写

模型很擅长补一个"看起来合理"的数字（比如"开机时间 < 25s"）。一旦阈值由代码预置，
`RESULT PASS` 就变成自我实现的预言。因此机制上强制：

- `assertions.tsv` 里没有生效行 → FEATURE 段固定 `SKIP` → 整体 `INCOMPLETE`；
- `--allow-skip` 单独使用会被拒绝（必须显式传 `--allow-incomplete` 才降级，且输出里会标注）。

宁可交不出结论，也不许编一个。

## 3. 退出码是接口，不是装饰

所有脚本共用一套退出码语义，调用方（人 / 上层脚本 / AI）按码决策，不靠猜日志：

| 码 | 含义 | 调用方应当 |
|---|---|---|
| `0` | 通过 / 成功 | 继续 |
| `1` | 断言失败（stale / 未找到 / 越界 / 漂移 / 有根失败） | 修问题 |
| `2` | 参数或配置错误 | 改调用方式 |
| `3` | **数据不可用**（工具缺失、库损坏、输出无法解析） | **记 SKIP/INCOMPLETE** |

把 `3` 和 `1` 分开是刻意的：库损坏不等于代码错了，设备没连不等于功能失败。
混在一起，人就分不清"要改代码"还是"要修环境"。

## 4. 为什么把树切成多个库

一个 300GB 的树建单库：首次索引几小时，`status` 几分钟，改一行要重扫全树。

切成按一级目录的库之后：

- `sync` 只碰你真正改动的那个根；
- `projectPath` 唯一，不会出现"拿 A 根的库查 B 根的符号"；
- 某个库坏了只影响一个根，重建代价可控。

代价是**必须路由**：任何查询前先确定归属根。这就是 `cg-route` 存在的原因，
也是为什么根清单是配置（`features/harness.conf`）而不是写死在脚本里。

> 同名子目录（如顶层 `packages/` 与 `frameworks/base/packages/`）按**最长前缀匹配**，
> 判据永远是 `cg-route` 的输出，不是路径里的字样。

## 5. 漂移守卫：为什么不用分支名

真实 BSP 常见"全树几十个仓同一个分支"（例如 `dis121c`），per-feature 分支并不存在。
所以基线记的是"**最后一次触及该路径的提交**"：

- 路径自己是 git 仓 → 记该仓 `HEAD`；
- 路径只是根仓的一部分 → 记 `git log -1 -- <path>`。

这样"别人在你范围外改了这些路径"会体现为漂移，"别处有新提交"不会误报。

`--strict` 下还会检查"范围外的脏文件"，允许清单按顺序取：

1. `features/<feature>/.drift-ignore`（每 feature 一份，优先）
2. `.drift-ignore`（树根一份，共用）
3. 都没有 → 内置默认（`AGENTS.md` / `CLAUDE.md` / `README.md` / `.gitignore` / `features/*`）

`.drift-ignore` 是**覆盖**而不是追加——不同项目需要不同的"允许脏"边界。

## 6. 新鲜度为什么看 mtime + git，而不是 `codegraph status`

`status` 在 3.2GB 的库上要 >2 分钟，放不进任何 hook。
`db mtime` 判"索引时间"，`git log -1` 判"代码时间"，两者比较足够判 `stale`，且是 O(1)。

代价要说清楚：**它不会告诉你库里少了哪些文件**。那种精查留给人手动跑
`codegraph status -p <根>`。

## 7. 诚实性铁律（写在测试里）

`harness/tests/test-harness.sh` 里有几条专门测"不许假绿"的用例：

- 空 `assertions.tsv` → 必须 `RESULT INCOMPLETE`，不是 PASS；
- 无 codegraph → STATIC 段必须 `SKIP`，不是 PASS；
- 指标列缺失 / 值为 `NA` → `SKIP`，不是 PASS；
- `--allow-skip` 单独用 → 必须 exit 2 被拒绝。

这些用例失败时，说明框架开始"帮你说好话"了，必须优先修框架。

## 8. 边界（刻意不做的事）

- `verify-build` **不执行构建**：不同 BSP 的构建入口差异太大，硬编码等于骗人；
- DEVICE 段只做只读查询，部署的 5 步事务契约写在 skill `deploy-and-accept` 里；
- 索引不含 git 历史语义：`stale` 只表示"代码比索引新"，不表示"索引错了"；
- 不猜设备：`adb` 相关工具都要求显式 `ANDROID_SERIAL`，多设备在线时拒绝执行。
